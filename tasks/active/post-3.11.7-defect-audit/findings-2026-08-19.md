# Post-3.11.7 defect audit — 2026-08-19

Ranked defects found by a post-merge audit of `main` after PRs #90, #91, and #92
landed, plus the release-prep pass that followed. Written while cutting `v3.11.7`
and **deliberately not fixed in it**: every item below is an AppleScript behavior
change that needs the same live verification the release itself got, and folding
eight unverified script edits into a tag would undo the point of the tag.

## What the audit cleared

These were the audit's primary targets and all came back clean, which is worth
recording because a clean result is the expensive kind to obtain:

- **Merge integrity.** All three branches cut from base `aa7fe0a` and merged in
  sequence. Every branch's source survived byte-identical into `main`; diffs of
  each branch tip against the merged tree over its own owned files are empty. The
  three branches had **zero source-file overlap**, so the semantic-conflict shape
  the audit was hunting never arose. The one post-merge source delta is the
  documented `compose/drafts_scripts.py` integration fix, which compiles under
  `osacompile` in both `dry_run` modes.
- **Bound and limit logic.** No zero, negative, or `None` limit reaches a scan on
  any path. 1536 builder parameter combinations produced 624 distinct scripts with
  0 literal slices below 1, 0 unbounded enumerations, 0 `whose` clauses, and 0
  `osacompile` failures.
- **Ratchet honesty.** The bare-`try` baseline moved 236 → 229 with four
  decreases, zero increases, and zero new modules. The hand-restated
  `PACKAGE_DIR`-namespace keys are correct.
- **Destructive tools do not report false success.** In `manage_trash` id-direct
  and `move_email` the counter increments after the mutation and inside the try,
  so the reported count stays honest; both print `REQUESTED IDS: N` beside
  `TOTAL: M`. `empty_trash` has no inner try, so `delete aMessage` fails loudly.
  Property reads run before the mutation in both, so preview and execute cannot
  diverge. The residual gap is a silent *partial* with no per-id reason, not a
  false success.
- **Suite.** 2174 pass, 0 fail, 0 skip. One warning, third-party
  (`pydantic_settings`), nothing repo-side.

## Ranked findings

### 1. `search_emails` answers `has_more: false` when it hit the scan wall
`tools/search/script.py` clamps the scan to `SEARCH_HARD_CEILING` (50) per
mailbox, but the tool's default `limit` is 100 and `tools/search/records.py`
derives `has_more` as `len(records) > limit`. Fifty records against a limit of
100 therefore returns `has_more: false` — an authoritative "that is everything"
produced after examining the newest 50 messages, alongside a `recent_days_applied`
that asserts a 90-day window was searched. `body_search_capped` and
`mailbox_count_capped` both have warning keys; the hard-ceiling clamp has none,
because the builder's return tuple carries no scan-ceiling flag. Paginating does
not escape it: `offset=30, limit=20` clamps back to 50 and reports `has_more:
false` again.

Pre-existing since v3.9.3, untouched by all three PRs. Highest blast radius of
anything here — it is every `search_emails` call — and it is precisely the
confident-wrong-answer shape this release exists to close.

### 2. `export_emails(scope="correspondent")` omits messages under a success banner
`tools/analytics/export_helpers.py` has five bare tries, each wrapping an entire
`repeat` over a recipient list and falling through to `return false`. A throw
excludes the message, never increments the matched count, and never reaches the
export-failure arm, so the output is the clean success path. Because the try wraps
the whole loop, one unresolvable recipient hides every later recipient in that
list. `address of aRecipient` is `missing value` for unresolved, distribution-list,
and X.500 entries, and `missing value contains "…"` raises −1700, so the trigger
is likely rather than theoretical.

This ranks second on consequence, not frequency: `plugin/skills/email-archive-cleanup/SKILL.md`
prescribes exactly this call as the evidence snapshot taken **before** an
irreversible `manage_trash(action="delete_permanent")`. A silent under-export
means mail is permanently deleted that was never written to disk.

### 3. `get_mailbox_unread_counts` can drop a mailbox, a subtree, or a whole account
`tools/inbox/unread_counts.py` wraps the per-account block, the per-mailbox read,
and the child enumeration in bare tries. An offline or mid-resyncing account
contributes zero rows and no marker. A per-mailbox throw drops that mailbox and
its entire child subtree, and with the default `include_zero=False` a dropped
mailbox is indistinguishable from a zero-unread one. The same file's
`summary_only` path does this correctly — `on error` appends `accountName &
":ERROR"`, mapped to `-1` in Python — so the nested path is inconsistent with its
own sibling twelve lines up. That sibling is the fix template.

### 4. `list_inbox_emails` renders a short list as complete
`tools/inbox/list_scripts.py`. The recent PR fixed the script-level swallow in
this builder; the per-message try one level in stayed bare, so rows drop silently.
Text mode emits `__COUNT__|||sentCount` next to a header built from
`messageCount`, and `tools/inbox/parsing.py` only splits the marker off — **the
two numbers are never compared**, so the data needed to detect the drop is already
on the wire and discarded. Sharpest with `read_status="unread"`, because
`unread_counts.py`'s own docstring designates that call as ground truth when the
cached unread count is suspect; the fallback authority under-reports too.

### 5. `get_email_thread` prints `FOUND N` then renders fewer than N
`tools/search/thread.py` prints the count, then a bare try in the render loop
drops rows against it. JSON mode returns rows with **no count at all**, so a JSON
caller gets a truncated thread with zero signal. The script-level handler never
sees it. The failure mode is a conversation summarized from an incomplete thread.

### 6. The `whose` lint is partially vacuous
`tests/core/test_no_unbounded_whose.py` is a raw line-by-line regex over file
text — no AST, no string-versus-code distinction. Four total evasions were
demonstrated end-to-end against the real test methods: adjacent-literal
concatenation even on a single line (`\w+` cannot match the closing quote), a
`whose` on a slice variable outside the hardcoded 11-name list, `messages ` and
`of MB` split across two Python lines, and a `contains_any_condition(` call
wrapped by a formatter. **A `ruff format` reflow of a long line is enough to
trigger the concatenation evasion by accident.** Three more forms — including the
most idiomatic spelling, `every message of mailbox "INBOX" whose …` — are caught
only by the raw-enumeration rule, which then names the wrong problem. Three of its
five rules are also still rooted at `TOOLS_DIR`, so `core/`, `bounded_scan.py`,
and `calendar_core/` are outside their scope.

Its sibling `test_no_bare_applescript_try.py` is sound by contrast: AST-based,
walks both `JoinedStr` and `Constant`, and detects 11 of 12 syntactic forms. That
is the shape this lint should be rebuilt into. Note the history — this lint has
already gone vacuous once, silently, through the whole v3.11.6 subject-filter bug.

### 7. `build_bounded_message_scan` has no stale-count guard, unlike both siblings
`bounded_scan.py`. PR #90 replaced the unbounded `messages of MB` fallback with
`messages 1 thru _mbCount of MB` and left it unguarded. The same PR added exactly
that guard in `tools/search/script.py` (nested try plus an `ERROR_MAILBOX` marker)
and `tools/compose/drafts_scripts.py` carries it too, with a comment stating the
reason outright: *"`count of messages` can still read stale-high, so the slice
keeps its own guard."*

Read carefully, this is **mostly a deliberate trade rather than an oversight**:
the module docstring argues that on a 24K Exchange mailbox the old spelling
"presents as a hang rather than an error, which is worse than failing," and a
stale-high count now surfaces as a loud caller-level error rather than a hang. The
part that is *not* covered by that reasoning is the `else` arm: a count that reads
**low or zero** on a non-empty mailbox now binds `{}` silently, where the old code
enumerated the real contents. Mail is documented in this repo to report cached
counts low — the unread count read 3,236 against a true 10,016 — so a stale-low
`count of messages` is plausible. It is not proven, and proving it needs a live
mailbox in that state.

### 8. `search_emails` record-emit loop drops messages that already matched
`tools/search/script.py`. A bare try wraps the emit loop for messages that have
**already matched** the filter, and `collectLimit` decrements inside the try after
the append, so a throw skips the row and the result set looks full-shaped with no
`PARTIAL:` line. The same module already implements the sanctioned channel for the
*filter* loop and at the mailbox level; only the render loop lacks it. PR #92 built
`records._read_failure_row()` for exactly this shape and wired it only into
`by_id.py`. Cheapest fix on this list.

## Suspected, unconfirmed

- **`manage_drafts(action="delete")` identity-drift guard weakened.**
  `tools/compose/manage.py`. The outer try fails closed — an empty
  `actualToAddresses` yields `DRAFT_DELETE_IDENTITY_DRIFT`. The inner bare try
  silently drops *one* recipient, which blinds the reverse "no unexpected actual
  recipient" check: the check that exists to catch a drifted draft carrying an
  extra recipient, and an unresolvable extra recipient is what a drifted draft
  would plausibly have. Narrow — subject, In-Reply-To token, and all expected
  recipients must still match — but it is a guard weakening on a destructive path.
  Not confirmed; constructing the drift state needs live mail.
- **Stale premise in a comment.** `tools/search/script.py` asserts that `manage/`
  and `analytics/` callers pass `date_from=None`. PR #91 made that false. The code
  is conditioned on `date_from` truthiness rather than caller identity, so nothing
  breaks — but it is the premise a future reader would build on.

## Verification status

Finding 7 was re-derived independently from the `v3.11.6..HEAD` diff and both
sibling call sites, including the trade-off reading and the stale-low hypothesis
that the audit did not raise. Findings 1, 2, and 6 were demonstrated by the audit
by executing the real modules and, for 6, by running the real test methods against
deliberately-bad samples. Findings 3, 4, 5, and 8 are source-level readings that
have not been executed. Nothing here has been exercised against live mail.

## Suggested order

8 and 4 are the cheapest and lowest-risk — 8 wires up a helper that already
exists, and 4 compares two numbers already on the wire. 2 and 3 have the clearest
user consequence and both have an in-repo fix template to copy. 1 is the widest
blast radius and needs a product decision about the response contract before it is
worth writing. 6 is a rebuild of the lint on the AST foundation its sibling
already proved, and it should come before any further AppleScript work, because it
is the thing that is supposed to catch this class in the first place.

## Live verification, 2026-08-19 (read-only, repo CLI)

Run against real Mail through `.venv/bin/apple-mail` and
`plugin/apple_mail_mcp.py --read-only`, never through the installed MCP plugin,
which is still v3.11.6 and would have returned a clean answer from stale code.
Six accounts; per-account unread totals byte-identical before and after, and no
message was opened, so nothing could be marked read.

**The release's own thesis holds under live execution.** `search_emails` ran
seven shapes across the subject fast path and the general path, 3.2–8.2s each,
with **zero out-of-window rows** in every row returned — including the sharp
case, a closed one-day window on a high-volume mailbox whose newest mail is
dated one day later: not one newer message leaked past the ceiling. Pagination
returned disjoint pages. Three genuinely empty mailboxes returned exactly zero
rows with no spurious single row, which is the `messages 1 thru 0` footgun not
firing. Six deliberately provoked errors all surfaced; none returned
empty-but-successful. Unread counts agreed across all six reporting surfaces for
the same mailbox, with the known-low cached value labelled rather than silently
corrected. `quick-check` passed 3/3 under threshold.

The one gap found — `inbox_dashboard`'s default UI mode carrying no provenance
at all — was fixed before the tag and is in the CHANGELOG.

### Lower-priority items from the same run

- **`search --json` has three different error envelopes.** Success uses
  `items`/`returned`; an account error uses `results`/`total` and a string
  `error`; a mailbox error uses neither and carries no machine-readable code.
- **The CLI exits 0 on every structured error**, so a shell caller cannot detect
  failure from `$?`.
- **`get_email_by_id` returns a bare `{"item": null}` for a nonexistent id** —
  no not-found signal, and no way to distinguish not-found from a read that
  threw. Its plural sibling `get_email_by_ids` does this correctly with
  `missing_ids` / `invalid_ids` / `errors`.
- **`serverInfo.version` reports the `mcp` library version, not the plugin
  version.** A client cannot tell an installed 3.11.6 from a repo 3.11.7 through
  the handshake — the exact drift hazard that forces live verification onto the
  CLI in the first place.
- **`get_statistics` still returns a derived `read` / `read_percent`** while its
  own note says not to derive a read count from the cached unread value. The
  payload is labelled; the derived field itself is not.
- **`search` reports `recent_days_applied: 0.0`** when the caller passed explicit
  `date_from` / `date_to`. Cosmetic.
- Finding 1 above was independently reproduced here: `has_more=false` on the
  subject fast path is scan-bounded, not window-exhaustive.

### Coverage this run did not provide

No sends, no drafts, no deletes, moves, or status changes — every destructive
path was deliberately left unexecuted. The non-positive cap refusals for
`max_deletes` / `max_moves` / `max_updates` therefore remain **source-verified
only**, as the CHANGELOG already states. The `move-dry-run` and `trash-dry-run`
CLI previews were skipped too: they advertise non-mutation, but that was not
first proved from source, and an advertised preview is not evidence. Full
`smoke-test` and `perf-test` tiers were not run.

**Suspected items, both confirmed and fixed.** The `manage_drafts` identity-drift
guard now fails closed with `DRAFT_DELETE_RECIPIENTS_UNREADABLE` *before*
`delete foundDraft`. The stale premise comment in `search/script.py` is corrected.

**Lower-priority items.** Fixed: the three `search --json` error envelopes, the
CLI exiting 0 on structured errors, `get_email_by_id`'s missing not-found signal,
`serverInfo.version` reporting the `mcp` library's version (it was `1.29.0`), and
`get_statistics`' unlabelled derived `read`. **Not changed:**
`recent_days_applied: 0.0` under explicit dates — on inspection the field is
accurate (zero recent-days window *was* applied, and `searched_from` carries the
real bound), so changing it would break a contract for no gain.

**Why `has_more` was left alone.** As a pagination bit it was already correct —
paging does advance through matches inside the scanned window. Forcing it true
whenever the ceiling fired would make it true on every page forever, since the
mailbox saturates the scan every time, so a caller looping until it went false
would never stop. That trades a wrong answer for a hang. The lie was that
`has_more: false` *reads* as "that is everything in the mailbox"; the fix is to
say which wall was hit.

**Found during the fix, not in the original audit.** The rebuilt lint surfaced
`get_inbox_overview(max_recent=...)` with no clamp anywhere in the package — a
large value enumerated an entire 25K-message Exchange inbox, the exact hang the
bounded-scan contract exists to prevent, reachable straight from a tool argument.
Fixed. Separately, `.claude/hooks/check_applescript_compiles.py` was found to
exit 0 having compiled nothing on five of the modules edited here — its loader
pre-registered a half-built module under its package-qualified name, and every
package here is a re-export facade, so the parent's `from .script import ...`
raised `ImportError`, which the hook reported as a skip. Fixed; coverage went
from 0 to 82 scripts across 36 modules, with a negative control proving it now
exits 2 on a deliberately broken `end try` in the module of the original 3.3.0
regression.
